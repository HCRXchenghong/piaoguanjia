## 1. 设计目标与约束

| 目标 | 落地方式 |
|---|---|
| 一人一账号，数据隔离 | 成员只能读写自己的票据；管理员可见全部 |
| 上传即识别，减少手填 | 三层离线识别链路，自动填 60%~80% 字段 |
| 识别必须离线 | Windows 内置 OCR + 自研 PDF 解析，不依赖任何云服务 |
| 成员二次确认 | 三步向导，识别结果只作草稿，提交前可任意修改 |
| 两类报销形态 | 采购（名称/类别/规格/链接/数量/税后单价/运费）与出行（时间/工具/路线/金额/出行人） |
| 状态双向维护 | 成员与管理员都能把票据改成「已报销 / 未报销」 |
| 管理端总表 | 按月、按年、按成员、按类别聚合，带图表 |
| 一键出表 | ZIP 内「附件重命名 + Excel 三表」 |
| 存储可控 | 永久保存或按天自动清理，清理范围可选 |
| 部署简单 | 单个 exe + 一个 MySQL + 静态前端，双击即启动 |

约束：主力运行环境 Windows 10/11（Ubuntu / macOS 亦可运行）、局域网部署、团队规模 10~50 人、单机 MySQL。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  浏览器（Vue 3 + Arco Design Vue + ECharts）                  │
│  · 登录 / 概览 / 上传向导 / 票据列表 / 成员 / 导出 / 设置        │
│  · JWT 存 localStorage，请求头 Authorization: Bearer <token>   │
└───────────────────────────┬──────────────────────────────────┘
                            │ JSON over HTTP（同源，无 CORS）
┌───────────────────────────▼──────────────────────────────────┐
│  Go 服务（net/http + 标准库 ServeMux 路由）                    │
│  ├─ middleware：日志 / panic 恢复 / 鉴权 / 管理员校验            │
│  ├─ api：认证、上传、票据、统计、成员、设置、导出、运维           │
│  ├─ ocr：PDF 解析 → WinOCR → 票面抽取                           │
│  ├─ storage：附件落盘、缩略图、保留期清理                        │
│  └─ exporter：ZIP + Excel（excelize）                          │
└───────────┬─────────────────────────────┬────────────────────┘
            │ database/sql                │ os/exec
┌───────────▼──────────────┐  ┌───────────▼───────────────────┐
│  MySQL 8.0（InnoDB）      │  │  PowerShell + Windows.Media.Ocr│
│  users / invoices / files │  │  （系统自带中文识别引擎）        │
│  pending_uploads / logs   │  └───────────────────────────────┘
│  settings                 │
└───────────────────────────┘
            │
┌───────────▼──────────────────────────────────────────────────┐
│  磁盘：data/files（原件）、data/thumbs（缩略图）、data/tmp     │
└──────────────────────────────────────────────────────────────┘
```

关键取舍：**不做前后端分离部署**。Go 进程同时提供 API 与静态资源，`web/dist` 直接托管，避免再装 Nginx；局域网部署少一个故障点。

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 后端 | Go 1.23 + 标准库 `net/http` | 单二进制、内存占用低、并发够用；`ServeMux` 自 1.22 起支持 `GET /api/invoices/{id}` 形式路由，无需 Gin |
| 数据库 | MySQL 8.0 | 团队已有运维习惯；utf8mb4 + InnoDB 事务；`JSON` 能力备用 |
| 数据访问 | `database/sql` + 手写 SQL | 表结构简单（6 张表），ORM 收益低；便于审查执行计划 |
| 认证 | PBKDF2-HMAC-SHA256（18 万轮）+ 自签 JWT（HS256） | 不引入第三方依赖；token 无状态，重启不失效 |
| Excel | `excelize/v2` | 纯 Go、无 CGO，支持样式、合并、冻结窗格、公式 |
| 前端 | Vue 3 + Vite + TypeScript | 团队熟悉；构建产物小（gzip 后主包 ~78KB） |
| UI | Arco Design Vue 2.59（按 Arco Pro 的布局规范搭建） | 中文场景组件齐全（表格、抽屉、步骤条、表单），视觉统一 |
| 图表 | ECharts 5 | 柱状图 + 环形图，够用且可定制 |

> 说明：官方 `arco-design-pro-vue` 模板锁定 Vite 3 / Node 16，在 Node 24 上安装与运行都有兼容风险，因此按 **Arco Pro 的设计规范**（深色侧边栏 + 顶栏 + 卡片式内容区）自行搭建，组件与主题仍全部来自 `@arco-design/web-vue`。

## 4. 数据模型

```
users ──1:N── invoices ──1:N── files
  │                │
  │                └── pending_uploads（上传暂存，提交后清除）
  └── audit_logs（谁在什么时候做了什么）
settings（键值对：团队名、类别、保留策略、识别开关…）
```

### invoices 核心字段

| 分组 | 字段 |
|---|---|
| 归属 | `user_id`、`status`（pending/reimbursed）、`deleted`（软删） |
| 类型 | `type`（procurement/travel） |
| 采购 | `title`、`category`、`spec`、`link`、`qty`、`unit_price`、`shipping`、`amount` |
| 出行 | `travel_time`、`transport`、`route`、`traveler` |
| 票面 | `invoice_no`、`invoice_code`、`invoice_date`、`seller`、`buyer`、`tax`、`total`、`invoice_kind` |
| 识别 | `ocr_engine`、`ocr_confidence`、`fields_json` |
| 审计 | `created_at`、`updated_at`、`reimbursed_at`、`reimbursed_by` |

设计要点：

- **金额只存一份** `amount`：采购 = 数量 × 税后单价 + 运费；出行 = 税后金额。避免"应收/实收"两套口径打架。
- **票面字段与业务字段分离**：`total`/`tax` 记录发票原值，`amount` 记录实际报销值，二者差异可追溯。
- **软删除**：删除只置 `deleted=1`，附件保留，误删可由管理员从库里找回。
- **索引**：`(user_id, deleted)`、`(status, deleted)`、`(invoice_date)`、`(created_at)`，覆盖列表与统计的常见过滤。

## 5. 离线识别链路（核心）

### 5.1 三层降级

```
① PDF 文字层解析      电子发票（数电票、增值税电子发票）→ 精确、零误差
        │ 文字少于 15 个汉字
        ▼
② PDF 内嵌图片 OCR    扫描件 PDF → 抽出 DCTDecode/Flate 图像 → OCR
        │
        ▼
③ 图片直读 OCR        JPG/PNG/WEBP/BMP → 预处理 → OCR
        │ 引擎不可用
        ▼
④ 放弃识别，返回空表单 + 提示，成员手动填写
```

为什么把 PDF 文字层放第一位：电子发票 99% 是矢量文字，直接读取比 OCR 准确一个数量级（发票号码、税号不会错一位），而且耗时只有 20~50ms。

### 5.2 PDF 解析器（自研，`internal/ocr/pdf.go`）

只实现发票场景需要的子集：

1. 扫描全部 `N G obj`，建立对象表；解析 `stream ... endstream`，支持 `FlateDecode`；
2. 展开 PDF 1.5+ 的 `ObjStm` 压缩对象流；
3. 从 `Root → Pages` 递归取页面，合并继承的 `Resources`；
4. 解析内容流：`BT/ET`、`Tf`、`Td/TD/Tm/T*`、`Tj/TJ/'/"`，记录每段文字的坐标与字号；
5. 字体解码：`ToUnicode` CMap（`beginbfchar`/`beginbfrange`）→ Unicode；简单字体支持 `/Differences` 与 GlyphName 映射；
6. 扫描件兜底：抽取 `/Subtype /Image` 的 XObject，`DCTDecode` 直接取 JPEG，`FlateDecode` 还原原始像素。

### 5.3 可插拔的 OCR 引擎

图片识别抽象成统一接口，按平台自动选择（也可在设置里手动指定）：

| 平台 | 引擎 | 依赖 |
|---|---|---|
| Windows | `Windows.Media.Ocr`（系统内置） | 无，中文语言包通常已装 |
| Ubuntu / Debian | Tesseract CLI（`chi_sim+eng`） | `apt install tesseract-ocr tesseract-ocr-chi-sim` |
| macOS | Tesseract | `brew install tesseract tesseract-lang` |

**Windows 桥**（`winocr.go` + `winocr.ps1`）：

- 通过 `os/exec` 调用 PowerShell，加载 `Windows.Media.Ocr`；
- 图片以 **base64 路径** 传入、结果写 **JSON 文件**，彻底规避中文路径与控制台编码问题；
- 单张耗时约 0.5~0.9s（含 PowerShell 启动）。

**Tesseract 桥**（`tesseract.go`）：

- `tesseract page.png stdout -l chi_sim+eng --psm 6 tsv`，解析 TSV 的单词级坐标；
- 按 `page/block/par/line` 聚合回「行 + 词 + 包围盒」，与 Windows 引擎输出同一结构，后续版面重建完全复用；
- 启动时探测可执行文件与 `--list-langs`，缺中文包会在设置页给出 apt 安装提示；
- PSM 默认 6，可用 `INVOICE_TESSERACT_PSM` 覆盖。

两个引擎共用一套预处理：< 1800px 时放大（CatmullRom）、灰度、1%~99% 直方图拉伸，模拟 200~300 DPI 的效果。
**PDF 文字层不依赖任何 OCR 引擎**，纯 Go 实现，跨平台一致。

### 5.4 版面重建与字段抽取（`parser.go`）

OCR 返回的是"单词 + 坐标"，直接正则匹配会错位。流程是：

```
tokens → 按 y 中心聚类成行 → 行内按 x 间距合并成单元格
       → 表头识别（项目名称/规格型号/单位/数量/单价/金额/税率/税额）
       → 数据行按 x 坐标就近归属到列 → 得到结构化明细
```

字段抽取策略：

| 字段 | 主策略 | 兜底 |
|---|---|---|
| 发票号码 | `发票号码[:]?\s*(\d{8,20})` | 全文找 20 位连续数字 |
| 开票日期 | `(20\d{2}年\d{1,2}月\d{1,2}日)` | ISO 日期 |
| 销售方 / 购买方 | 定位「销售方」行，取「名称:」后的值 | 取标签后剩余文本 |
| 价税合计 | `价税合计/小写 + 金额` | 中文大写金额转换（贰佰肆拾贰圆玖角伍分） |
| 金额 / 税额 | 「合计」行里的两个金额 | — |
| 明细行 | 表头列坐标映射 | 正则 `数量 单价 金额` 三连 |
| 出行要素 | 出发站/到达站、车次、乘车人、乘车日期 | 关键词推断交通工具 |

**置信度**：每个字段返回 0~1 的 confidence（标签命中 0.98、模式匹配 0.6、全文兜底 0.55…），并用「金额 + 税额 = 价税合计」做勾稽校验，通过则提升到 0.95。前端据此显示「已识别 / 请核对」。

### 5.5 识别效果（实测示例）

样例 `samples/示例发票-采购.png`（1654×2339 渲染图）：

```
engine: windows-ocr   confidence: 0.88
发票号码 26442000000123456789   开票日期 2026-10-21
销售方 上海云帆办公用品有限公司   价税合计 ¥242.95
明细 A4复印纸 | 70g 500张/包 | 数量 10 | 单价 21.50 | 金额 215.00 | 税率 13%
→ 表单建议：名称 A4复印纸，类别 办公用品，数量 10，税后单价 24.30，金额 242.95
```

## 6. 业务流程

### 6.1 提交一张发票

```
选择文件 ──► POST /api/uploads ──► 落盘 tmp + 识别 + 返回 token & 解析结果
                                      │
           前端 prefill 表单 ◄────────┘
                    │
        成员核对/修改（可切换采购/出行）
                    │
        POST /api/invoices{payload, uploads:[token]}
                    │
        校验 → 事务写 invoices → tmp 文件移入 files/ → 删 pending
                    │
             返回完整票据对象
```

为什么分两步上传：识别要 1 秒左右，先上传先出结果，成员改完再提交；提交时只传 token，不重复传文件。

### 6.2 金额对齐规则

税后单价 = 价税合计 ÷ 数量，四舍五入到分；若「数量 × 单价 + 运费」与票面价税合计相差 ≤ 1 元，**以票面金额为准**，向导里会提示「已对齐票面价税合计」。财务口径以发票为准，避免 1 分钱对不上账。

### 6.3 状态流转

```
pending（未报销） ⇄ reimbursed（已报销）
```

成员可在「我的发票」自助切换，管理员可在列表/详情/成员维度切换，每次变更写审计日志并记录 `reimbursed_at` / `reimbursed_by`。

## 7. 权限与安全

| 项 | 做法 |
|---|---|
| 口令存储 | PBKDF2-HMAC-SHA256，18 万轮，16 字节随机盐，存 `pbkdf2_sha256$轮数$盐$摘要` |
| 会话 | JWT HS256，7 天有效期，密钥首次启动生成并写入 `data/jwt.secret` |
| 越权防护 | 所有票据/附件接口先查 `user_id`，非本人且非管理员直接 403 |
| 上传校验 | 以**文件头**判定类型（不信任扩展名），限制 20MB / 8 个附件 |
| 登录爆破 | 同 IP+用户名 5 分钟内 10 次失败即锁定 |
| 文件访问 | 附件只通过 `/api/files/{id}` 输出，路径由数据库 id 映射，无目录穿越 |
| 注入 | 全部 SQL 参数化 |
| 审计 | 登录、提交、修改、删除、导出、成员变更、设置变更全部落库 |

部署建议：默认监听 `0.0.0.0:8686`，仅限内网；如需公网访问，用 Nginx 反代 + HTTPS + 访问控制，不要把 8686 直接映射出去。

## 8. 导出设计

一次导出 = 一个 ZIP：

```
附件001_办公用品_242.95元.pdf     ← 序号与 Excel 行号一致
附件002_差旅交通_74.50元.png
附件002_差旅交通_74.50元_2.png    ← 一张票据多个附件时加后缀
01_采购报销明细.xlsx              ← 采购列：名称/类别/规格/数量/单价/运费/金额…
02_出行报销明细.xlsx              ← 出行列：时间/工具/路线/出行人/金额…（无数据时不生成）
导出说明.txt
```

每种类型一个工作簿，各含三个工作表：

1. **明细**：按类型定制的列（采购 17 列 / 出行 15 列），表头冻结 + 自动筛选 + 合计行（写死数值，避免公式没有缓存值时显示空白）；
2. **汇总**：按上报人统计票据数、未报销、已报销、合计；
3. **统计**：采购按类别、出行按交通工具统计金额与占比。

采购与出行不混在一张表里；哪一类没有数据就不生成对应文件。导出范围由前端筛选条件决定（月份 / 年份 / 自定义区间 / 全部 + 类型 + 状态 + 成员），文件名与表头里都会带上区间和状态；后端复用列表的过滤构造器，保证「看到的」和「导出的」一致。

## 9. 存储与保留

- 附件按 UUID 命名存放在 `data/files`，数据库只存 `storage_name`；
- 缩略图按需生成并缓存到 `data/thumbs`（PDF 取首页内嵌图）；
- 保留策略：
  - `permanent`：永不清除（默认）；
  - `auto`：超过 N 天的数据，可选「只删原件保留台账」或「连记录一起删」；
  - 每 6 小时检查一次，也可在设置页手动触发；
- 备份：`data.json`（用户/票据/设置）+ 全部附件打包下载。

## 10. 性能与容量

| 指标 | 实测 |
|---|---|
| 列表接口（1000 张票据） | < 10ms |
| 统计接口（按月/类别/成员聚合） | < 15ms |
| 单张图片识别 | 0.5~0.9s |
| 单页 PDF 文字层解析 | 20~50ms |
| 记忆体占用 | 空载约 20MB |
| 导出 100 张票据（含 200MB 附件） | 3~8s，内存峰值约 300MB |

容量估算：50 人 × 每年 200 张 × 1MB ≈ 10GB/年，单机 MySQL + 本地磁盘足够；超过 10 万张时再考虑分表或对象存储。

## 11. 部署与运维

**本机/局域网**

1. 双击 `启动.bat`（自动拉起 MySQL 与 Go 服务）；
2. 浏览器访问 `http://127.0.0.1:8686`，初始化管理员；
3. 其他同事用 `http://<本机IP>:8686`。

**迁移到服务器**

1. 目标机装 MySQL 8，执行 `server/migrations/000_bootstrap.sql` 建库建账号；
2. 拷贝 `server/bin`、`web/dist`、`server/data`（附件）；
3. `invoice-server.exe -addr :8686 -web web/dist -dsn "user:pass@tcp(host:3306)/invoice?..."`；
4. 需要开机自启时用 `nssm` 或计划任务注册为服务。

**日常运维**

- 备份：设置页一键下载，或定时复制 `server/data` + `mysqldump`；
- 日志：控制台输出请求日志（`-debug` 打开全部），审计日志在设置页可查；
- 升级：替换 exe 与 dist，执行增量 SQL 即可，前端无状态。
